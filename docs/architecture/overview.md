# System Overview

The Acquisition Platform is a data-dense, highly interactive Next.js application designed to manage the end-to-end lifecycle of multifamily real estate acquisitions. It replaces fragmented workflows (spreadsheets, disconnected emails, ad-hoc file storage) with a single, secure source of truth.

## 1. Core Technology Stack

*   **Framework:** Next.js 16.2.6 (App Router with Turbopack)
*   **Database & Auth:** Supabase (Postgres 14+, GoTrue)
*   **Styling:** Tailwind CSS v4 (`@tailwindcss/postcss`), custom CSS variables, Shadcn UI
*   **Data Fetching:** React Query (`@tanstack/react-query`) for client-side server state management.
*   **Integrations:** 
    *   Google Workspace (Gmail API, Drive API)
    *   Cloudflare Turnstile (Bot protection)
    *   Upstash Redis (Rate limiting)
    *   ExcelJS (CoStar file parsing)

## 2. Next.js Routing Architecture

The application strictly organizes its pages into three distinct Next.js Route Groups. This segregation allows for differing layouts, error boundaries, and visual shells.

1.  **`(auth)`**: Public routes for authentication (`/login`, `/signup`, `/reset-password`). These routes are entirely unauthenticated and feature a full-screen, focused layout.
2.  **`(internal)`**: Views exclusively for the internal acquisition team (`/dashboard`, `/deals`, `/campaigns`, `/import`, `/settings`). Features the persistent dark sidebar layout.
3.  **`(client)`**: Views exclusively for the CEO/investor client (`/overview`, `/calls`). Features a simplified header layout without the complex sidebar.

## 3. The Proxy Pattern (Replacing `middleware.ts`)

In Next.js 16, conventional `middleware.ts` logic has been shifted. The platform uses a **Proxy Pattern** located at `src/proxy.ts` to handle session hydration and access control before rendering.

### How `proxy.ts` works:
1.  **Session Hydration:** It calls `updateSession()` from `@supabase/ssr` to ensure the auth token cookie is fresh.
2.  **Role Extraction:** Instead of making a database round-trip to the `profiles` table, it reads the user's role directly from the JWT's `app_metadata`:
    ```typescript
    const role = (user as UserWithRole)?.app_metadata?.role
    ```
3.  **Strict Gating:**
    *   Unauthenticated users attempting to reach `(internal)` or `(client)` routes are bounced to `/login`.
    *   Authenticated users attempting to reach `(auth)` routes are bounced to their respective home pages (`/dashboard` for internal, `/overview` for clients).
    *   Cross-role pollution is blocked: internal users cannot access `/overview`, and clients cannot access `/dashboard`.

## 4. Key Integrations & Subsystems

### A. CoStar Import Pipeline
The platform allows internal users to bulk-import property leads.
*   Users upload an `.xlsx` file generated by CoStar.
*   `exceljs` parses the file in-memory.
*   The system cross-references `property_id` against the database to prevent duplicate ingestion.
*   A background polling mechanism tracks the import progress to bypass Vercel's 60-second function timeout limits.

### B. Google Workspace Automation
*   **OAuth & Tokens:** Users authenticate via Google OAuth. Offline refresh tokens are stored securely in `google_tokens`.
*   **Gmail Push Notifications:** Instead of constantly polling the Gmail API, the platform calls `gmail.users.watch()` to subscribe to a Google Cloud Pub/Sub topic.
*   **Pub/Sub Webhook:** When a contact replies to an outreach email, Google sends a webhook to `/api/emails/webhook`. The system verifies the Google JWT, fetches the message delta, and marks the deal as "Replied".
*   **Google Drive:** The platform automatically provisions Google Drive folders for new deals (`POST /api/deals/[id]/drive`), sets them to "anyone with the link can view", and attaches the URL to the deal record.

### C. Rate Limiting & Bot Protection
*   **Cloudflare Turnstile:** Used on the `/login` and `/signup` routes. Forms cannot be submitted until Turnstile passes, and the backend verifies the token using the `TURNSTILE_SECRET_KEY`.
*   **Upstash Redis:** Prevents abuse using sliding window rate limits. E.g., `loginRateLimit` blocks IP addresses after 5 failed attempts in 15 minutes, and `emailSendRateLimit` caps users at 100 outreach emails per day.
